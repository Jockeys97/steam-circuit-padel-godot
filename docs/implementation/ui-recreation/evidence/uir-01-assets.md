Source decision (recorded, not silent): the ticket's proposed `ofl/nunito/static/Nunito-*.ttf` URLs **404** — the repo carries only `Nunito[wght].ttf` and `Nunito-Italic[wght].ttf` (verified against the GitHub contents API). `https://fonts.google.com/download?family=Nunito` returns an HTML page, not a zip (verified: HTTP 200, `content-type: text/html`), so that fallback is unusable from this Mac. The statics were therefore taken from Google's own CDN through the fonts.googleapis.com v1 CSS API with a legacy User-Agent, which serves the **static per-weight TTFs** of the exact family and weights the reference requests (`index.html:13-16`: Lilita One 400, Nunito 400/600/700/800). No family was substituted.

Two findings worth carrying forward:

1. The Google-hosted Nunito statics keep the upstream variable font's odd `name` records (`Nunito ExtraLight …`), while `OS/2.usWeightClass` carries the correct 400/600/700/800. Godot matches fonts by resource, not by family name, so the theme references each file explicitly; the weight classes are what the probe/theme use to tell them apart.
2. These statics are the **latin subset** (230 codepoints). Coverage was checked against the reference's own text corpus (every character in `index.html`, `styles.css` and `js/**`, 147 distinct characters): **zero missing below U+2000** — Italian and English copy renders completely. The 37 missing codepoints are symbols/emoji (`← ↑ → ⌘ ✕ ✓ ▣ ☰ 🔊 🎮 🏆` …); the browser does not render those from Lilita One/Nunito either (Google's latin subset excludes them) — it falls back to a system font. The port must reproduce that fallback (UIR-02 declares a SystemFont fallback; screens never draw those glyphs from the display/body faces).
