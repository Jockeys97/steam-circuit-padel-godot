## 2. Disagreements / contradictions

1. **Does Astra under-delegate or over-delegate?** Official guidance (F9: "may delegate less often than some multi-agent workflows expect") vs field reports of heavy subagent spawning (F12 Kilo "leans heavily on subagents"; F13 HN "spawns subagents a lot… good coordinator but even more cost"). Resolution candidate: it is harness/config-dependent (Codex vs API vs router setups); the safe move is explicit *conditions* for delegation plus a budget cap, not a blanket "use subagents" or "delegate less".
2. **Stops too early vs refuses to stop.** OpenAI's dev blog (F19) and codewithseb (F22) report early stopping/decline; Kilo (F12) frames early give-up as a deliberate honesty tradeoff. Yet HN (F25) and the tabbit Reddit report (F17) describe the opposite: goldplating, "one more thing", 6-hour rebases, unfinished 70-hour refactors. These are reconcilable: review-gate language and narrow goals pull the stop earlier (F19), while broad open goals + thoroughness bias pull work longer; both failure modes coexist under different framings — which is exactly why "define completion" and explicit exploration bounds (F35) recur.
3. **Delete scaffolding vs write large structured prompts.** OpenAI/Kilo/codewithseb say subtract instruction files and guardrails (F20, F21, F22); meanwhile most 2026 guides (F1, F4, F5, F6, F27) hand you a 10–22-block mega-prompt. Reconciliation visible in the sources themselves: what should be deleted is *failure-compensating* scaffolding (scope-drift watchers, "be sure to test" nudges); what stays or gets added is *behavioral policy* (priority, autonomy, delegation triggers, stop conditions, verification scope). F1 states this explicitly: "each block corresponds to a realistic failure mode. If a task does not have that failure mode, remove the block."
4. **Strengthen verification vs reduce testing.** OpenAI (F20) says the old "run tests / be thorough" encouragement now causes over-testing; agiflow/jovanipink/atlascloud/saulius (F36, F37, F42, F43) say add independent verification, evidence contracts, and never weaken assertions. They agree on the axis: *verification independence and evidence quality up; verification breadth for low-risk changes down* (F1's "verification proportional to risk" formula resolves it).
5. **Scope-drift guards: remove vs keep.** codewithseb (F22) says delete them (0% scope violations, vendor-reported); agiflow/jovanipink (F36, F42) insist boundaries/authority records remain necessary. Reconciliation: model-level drift improved, but accountability controls serve a different purpose (who may do what, what counts as done) and are not the same artifact as drift watchers.
6. **Who judges "done": deterministic checker vs LLM judge vs self-report.** auravcs (F39) and vanja (F38) warn that LLM judges and self-assessment are gameable/goodhartable; yet goal-loop products (knightli F40, sean-weldon F41, Hermes/Codex `/goal` guides) run LLM judges over the transcript. Consensus that does emerge: make "done" observable in the evidence surface (commands, outputs, counts) regardless of who judges, and prefer deterministic checks where they exist.
7. **Reasoning effort**: practitioners in F4 and F17 converge on medium/high as default with escalation only after failure (XHigh "no obvious gain"), and codewithseb (F22) notes all headline benchmarks are max-effort and `max` costs ~2.3× `low`. Contradicts advice to "just use max" — flagged as cost trap.
8. **Vs OpenAI official guidance — one direct caution:** F34 technologye's executor prompt says "Do not stop at a proposed plan when you can proceed." For a *plan-creation* mission this is exactly backwards per OpenAI's own warning (F19) that a review-stop requirement pulls the model toward an earlier stopping point — both statements can't be applied to the same prompt. Pick the stopping-point language that matches the deliverable (plan vs implementation).

## 3. Most repeated patterns across independent sources

1. **Define "done" before starting, with evidence that can be inspected** (OFF F19; SEC F4, F27, F36, F39–F41; COMM F14, F17). Every source that discusses long-horizon work lands here; the strongest versions name the exact command/artifact a verifier can re-run.
2. **Explicit autonomy policy: act on reversible/authorized work, ask only when a missing fact *materially* changes outcome, gate irreversible actions** (OFF-attributed F4–F6, F26; SEC F1, F3, F7, F11).
3. **Instruction priority clause** — task instructions outrank skill/AGENTS/docs; on conflict, *name the file and continue* rather than stalling (F2, F5, F6, F7, F23, F24, F30).
4. **Delegation needs triggers, a structured return format, and one owner of synthesis** — plus "don't delegate coupled work" and task packets instead of shared context (F10, F11, F14, F15, F16; primary-agent-owns-reconciliation stated in both official-derived and independent guides).
5. **Verification proportional to risk of the change; independence beats intensity** — separate verifier context, never self-certify; stop only on the verifier's verdict (F1, F20, F36, F37, F43).
6. **Stop conditions in two terminal states: success-on-evidence and blocked-on-conditions** (budget exhausted, two iterations no progress, flaky evidence, required scope violation → report blockers) with an explicit human escalation path (F36, F39–F41, F44).
7. **Plan/execute split with lean, fresh-context, single-responsibility workers; the durable orchestrator keeps plan state and bookkeeping** (F14, F15, F18, F33, F43).
8. **Smallest-change / anti-goldplating clause** ("minimum change… list unrelated issues, don't fix them") — now considered mandatory because of Astra's over-engineering bias (F6, F21, F22, F25; plus OpenAI's FrontierCode dev message, reported in F12/F21).
9. **Verbatim phrasings worth carrying over** (appear repeatedly): "Infer my intent… and proceed to completion unless the action is hard to reverse"; "Ask for clarification only when the missing information could materially change the outcome"; "Complete the work that is already authorized… before asking for approval"; "Do not search to confirm… behaviour you already know"; "name the source and explain why" when a conflict pauses work; "Lead with the result… report what changed, what was verified, any remaining uncertainty."
10. **Format/verbosity is configuration, declared up front** — prose-first rules, stock-phrase blocklist, result-first structure (F1, F11, F28).

## 4. Implications for the v1 Astra plan-creation prompt (short)

The v1 prompt already carries: role + mission, context/why, FIELD LAW hard constraints, explicit questions, known failure examples, constraints, deliverables, output format, and a checkpoint/verification rule with "regenerable handle" evidence and "never self-certified green". Relative to the survey, the consistently-reported gaps are:

1. **No instruction-priority clause** — the prompt references repo docs, BRIEF/README, CHARTER, and mission tools; nothing states that *this* task prompt outranks conflicting skill/docs guidance, nor "name the conflicting source and proceed" (pattern 3). This is the single most-repeated fix and the one the v1 prompt lacks entirely.
2. **Delegation policy is implicit** ("cheap workers doing the legwork") — survey pattern 4 suggests: name when to parallelize vs keep, the worker task packet (goal/anchors/allowed files/expected evidence/return schema), and that Astra owns reconciliation and the final plan.
3. **Stop/blocked condition is half-specified** — "Pause only for destructive actions, real scope conflicts, or decisions only a human can make" tells it when to pause but not the *blocked* terminal state (what to report when a question can't be answered with evidence within budget) — pattern 6 wants "report attempts, evidence, remaining uncertainty, exact blocker, smallest input needed".
4. **Plan-vs-execution boundary should be explicit in the plan-creation direction** — F19's warning means the current "Produce the implementation plan and tickets" may still invite implementation drift unless the prompt says the deliverable *ends* at plan+tickets and what "done planning" means (e.g., all five explicit questions answered with evidence plan, per-ticket DoD/verification commands) — cf. F30 "just plan" vs "implement and verify locally".
5. **No minimality clause** — but note this mission is plan-creation: the minimality instruction belongs in the *ticket/prompt template for the worker prompts and in "what the plan must not do"* (don't invent extra arenas, don't plan regressions to frozen files) — mirrors F21 phrasing ("make the minimum change… list unrelated issues, don't fix them").
6. **Verification phrasing is already strong**; the survey adds two small upgrades: state the verification *surface* per ticket (exact command + expected output, F36/F38) and require the plan to say which checks are deterministic vs judge-based vs ad-hoc (F39), which the v1 already gestures at ("what stays ad-hoc").
7. **Effort/latency**: F17/F22 suggest low/medium reasoning + escalation for planning-type runs is a live practitioner option given Astra's planning strength at medium (F30); worth an A/B rather than defaulting to max.

## 5. Method, limits, uncertainty

- **Fetches:** 4 web searches, 2 multi-URL extract batches (9 pages), 1 single-URL extract batch (2 pages), 1 X search; plus 2 local cached guides (promptessor) read directly. Total network fetches ≈ 16, within the 15–25 cap.
- **X/Twitter:** x_search returned a synthesized answer with zero citations (`degraded: no citations returned`) — **excluded as evidence**; no citable X posts are claimed in this report.
- **Likely content-farm overlap:** acecloud, usingclaude, treerouter, dev.to, dmarketertayee, atlascloud, axiabits, and prompTessor (partially) all appear to recycle the same OpenAI-derived five-behavior framing (and each other's prompt blocks). They are listed as *independent-ish* only where wording differs; treat "multi" claims sourced from these as "one upstream source, many republishers."
- **Anecdote weighting:** HN comments and the Reddit curations are single-user reports (allowance burn, goldplating, test-suite loops). They are marked `anec` and should be treated as hypotheses, not measurements.
- **Undated sources:** several useful stop-condition/verification posts (saulius.io, jovanipink, vanja.io, auravcs, ylanglabs, joaoqueiros, mindstudio, singularitymoments, atlascloud) carry no visible date; they are current-era by content (they reference `/goal`, Astra, or 2026 harnesses) but predate-or-postdate Astra is unverified. The oldest dated sources cited (knightli 2026-05-26, sean-weldon 2026-05-10, OpenAI GPT-5 cookbook) are pre-Astra and included only where their patterns are model-agnostic.
- **Vendor-reported figures** (48%→0% scope violations, 0% out-of-scope, benchmark deltas) originate from OpenAI or from articles citing OpenAI; repeated here as *reported*, not verified. codewithseb (F22) itself cautions: all headline scores are max-effort, some error bars overlap, and one benchmark set diverges in opposite directions.
- Nothing in this report was verified by running Astra; this is a literature survey only.
